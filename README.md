# Healthcare Claims Prediction and Weekly Forecast on a Small Dataset

> **All data in this repository is synthetic.** `data/claims.csv` is generated by
> `python claims_ml.py generate` from the random process in that function. It contains no real
> members, providers, claims, or protected health information, and it was never derived from
> any real dataset. Numbers in this README describe model behaviour on that synthetic data
> only. See `data/README.md`.

A complete, local, CSV-in / CSV-out machine-learning package for a health-insurance
claims dataset of roughly 10,000 rows. No database, no cloud dependency, no GPU.
One Python file, one notebook, one data file.

It ships three models and a weekly learning loop:

| Model | Question it answers | Type |
|---|---|---|
| `model_denial` | Will this claim be denied? | classifier, gives P(denied) |
| `model_paid` | If approved, how much will we pay? | regressor with a 90% prediction interval |
| weekly forecast | How many claims and how many dollars next 4 weeks? | time-series ensemble, backtested, with intervals |

Expected paid per claim = `(1 - P(denied)) * paid_if_approved`. This "hurdle" split is
deliberate: mixing zeros from denials into a dollar model is the most common reason a
claims regression looks bad.

---

## 1. Quick start

```bash
pip install -r requirements.txt

python claims_ml.py generate          # synthetic data/claims.csv (skip this: drop in your own)
python claims_ml.py train             # ~70 s: CV, tuning, holdout metrics, saves models
python claims_ml.py forecast          # ~25 s: rolling-origin backtest + next 4 weeks
python claims_ml.py simulate          # ~15 s: replay the weekly loop over the last 8 weeks

python claims_ml.py predict open_claims.csv    # score new claims -> predictions.csv
python claims_ml.py update this_week.csv       # the weekly loop (see section 7)

jupyter notebook claims_forecast.ipynb          # the same, with charts and commentary
```

`train --fast` skips hyperparameter search and CV repeats and is what the notebook uses
(30 s to 2 min depending on cores). Add `--as-of 2025-12-28` to `forecast`, `update` or
`simulate` when your extract is not complete through the end of its last week.

| random forest | 235 | 1,364 | 0.133 | 0.125 | 0.969 | 49% |

| hist gradient boosting, raw | 246 | 1,569 | 0.140 | 0.120 | 0.959 | 51% |

The candidates are statistically indistinguishable (bootstrap MAE intervals overlap; see
`metrics_regression.csv`), which is expected at this data size.
90% prediction interval: covers **94.8%** of holdout actuals, median width $119.
The selected model is the plain boosted model because the tuned and stacked variants were
within 2% of it in cross-validation and it is 300x smaller on disk (see `SIMPLE_TOLERANCE`).
A smearing factor of x1.03 (stored in the model file) corrects the small under-prediction
that every log-target model has after transforming back to dollars.

**Expected paid over ALL holdout claims, denials included: MAE $787, WAPE 0.51.**
This is the number to quote when the question is "how much will we pay in total", because
`expected_paid = (1 - P(denied)) * paid_if_approved` carries the denial model's uncertainty.
It is much worse than the approved-only number because denial is only moderately predictable
here (PR-AUC 0.51): a $20,000 claim with a 30% denial probability is off by $6,000 or
$14,000 whichever way it lands. Improving the denial model is the biggest lever on this number.
It also lives in `metrics_regression.csv` as the row `expected_paid (all claims)`.

**Weekly forecast, rolling-origin backtest: 12 origins x 4 weeks ahead**

| series | best model | MAE | MASE | WAPE | 90% interval coverage |
|---|---|---|---|---|---|
| paid $ / week | ensemble (seasonal naive + Fourier ridge) | $38,108 | 0.48 | 0.236 | 85% |

## 4. How it works

```
claims.csv (one row per adjudicated claim)
   |
   v
make_features()  ---- derived: log_billed, billed_per_unit, deductible_ratio, calendar ----
   |
   |-- time split: everything before the last 12 weeks = train, last 12 weeks = holdout
   |
   |-- [paid model, approved claims only]                    [denial model, all claims]
   |     repeated 5x2 K-fold CV over 5 candidates              repeated CV over 4 candidates
   |     random search on boosted model (20 draws)             select by PR-AUC
   |     stack of top 3                                        threshold = best F1 on CV probs
   |     select by CV MAE, prefer simpler within 2%
   |     conformal interval from CV residuals (log space)
   |     permutation importance on holdout
   |
   |-- holdout metrics for EVERY candidate (never used for selection)
   |-- refit winners on all rows -> model_paid.joblib, model_denial.joblib
   |
   v
weekly_series()  ---- complete weeks only; partial last week dropped ----
   |
   |-- 7 forecasters: naive, seasonal naive, 4-wk mean, damped Holt, Fourier ridge,
   |   boosted lags, ensemble
   |-- rolling-origin backtest, 12 origins x 4 steps -> forecast_metrics.csv
   |-- best by MAE; interval from its backtest residuals (leave-one-origin-out coverage)
   v
forecast_next.csv
```

## 5. The small-data playbook (what is already in the code)

Ten thousand rows is small for anything with a heavy tail. Everything below is implemented;
the order is roughly by how much it mattered on this data.

1. **Model the mechanism, not the number.** Denial and payment are two different processes,
   so they get two models. A single regression on `paid_amount` with 12% zeros looks 30%
   worse for no reason.
2. **Log-transform the dollar target** (`TransformedTargetRegressor` with `log1p`). Claim
   amounts span $20 to $120,000. Without the log, every model chases the ten largest claims.
3. **Monotonic constraints from domain knowledge** (`MONO` dict). Paid cannot go down when
   billed amount, billed per unit or length of stay go up, or go up when remaining deductible
   (or deductible as a share of billed) goes up. The boosted model is forbidden from learning
   otherwise, and the constraint is verified on the shipped model: 0 violations in 300 claims
   swept across each feature. Constrain the derived ratios too, or the model routes around the
   raw-feature constraint. This is free robustness on small data: it removes whole families of
   spurious splits, at a cost of a few dollars of MAE here.
4. **Strong regularisation by default**: shallow trees (depth 4), leaves of 25+ rows,
   L2 penalty, early stopping on a validation slice. The random search explores from there,
   never from "unlimited depth".
5. **Repeated K-fold, not one split.** With 8k training rows a single 80/20 split moves MAE
   by 10% from seed to seed. 5 folds x 2 repeats gives a mean and a standard deviation, and
   selection uses the mean.
6. **Time-based holdout.** The last 12 weeks are never seen during selection. That is the
   number to quote to the business, not the CV number.
7. **Prefer the simpler model within tolerance** (`SIMPLE_TOLERANCE`). A stack of three
   models that is 1% better in CV is usually 0% better next quarter, and 300x larger.
8. **Prediction intervals, not just points.** Conformal: take the 90th percentile of absolute
   log residuals from cross-validation and apply it symmetrically in log space. Cheap,
   distribution-free, and the holdout confirms the coverage (94.8% for a 90% target).
9. **Cap predictions** at 2x the largest paid amount ever seen, and **correct the
   log-transform bias** with a smearing factor so predicted totals sum to actual totals.
10. **Missing values are handled, not dropped.** Numerics are median-imputed; missing or
    unknown categories become a "missing" category the boosted trees learn a direction for.
    No row is thrown away.
11. **Domain features > more rows.** `billed_per_unit`, `deductible_ratio`,
    `prior_paid_per_claim` each carry more signal than a thousand extra rows.
12. **Seasonal naive as a forecasting candidate.** On 2 years of weekly history it is very
    hard to beat "same week last year", so it is in the race and in the ensemble.
13. **Baselines everywhere.** Median predictor, prior-rate classifier, naive forecast. If a
    model does not beat these by a wide margin it does not ship.

What to try next if you need more (roughly by expected payoff):

- **More history for the forecaster.** Two years is the minimum for weekly seasonality;
  three to five years lets the ML forecasters overtake seasonal naive.
- **Large-claim pooling for the dollar forecast.** Forecast "core" spend (claims under the
  99th percentile, about $50k here) with this pipeline and forecast the count of large claims
  separately as a Poisson process times their mean. Weekly dollars are noisy only because of
  the tail.
- **Target encoding for high-cardinality columns** (provider ID, ICD code) if you have them.
  Do it inside the CV folds or it leaks.
- **Quantile regression** (`HistGradientBoostingRegressor(loss="quantile")`) for asymmetric
  intervals if the symmetric log interval is too wide on cheap claims.
- **Monotonic constraints on more features** once you have confirmed the direction with the
  business (for example `in_network` should only raise paid).
- **Group K-fold by member** if members recur often, so the CV is not flattered by seeing
  the same person in train and test.

## 6. Metrics glossary

Every metric in the CSVs, what it means, and what "good" looks like for claims.

### Paid amount (regression)

| metric | meaning | read it as |
|---|---|---|
| **MAE** | mean absolute error in dollars | the headline. "We are off by $242 per claim on average" |
| MAE_CI95_low / high | 95% bootstrap interval of MAE | if two models' intervals overlap, they are not distinguishable on this holdout |
| **RMSE** | root mean squared error | punishes big misses; RMSE much larger than MAE = a few catastrophic claims dominate |
| MedianAE | median absolute error | the typical claim; unaffected by the tail |
| MaxAE | largest single miss | the worst case; usually one inpatient surgery |
| **WAPE** | sum of abs errors / sum of actuals | dollar-weighted % error; the best single number for finance. 0.137 = 13.7% of total spend |
| sMAPE | symmetric mean abs % error | per-claim %; bounded 0 to 2; robust to zeros |
| MAPE_y>=50 | mean abs % error on claims >= $50 | classic MAPE, but only where it is defined; ignore for cheap claims |
| **R²** | variance explained | 0.96 here; anything above 0.7 on real claims is strong |
| ExplainedVar | R² ignoring bias | if this is much higher than R², the model is biased |
| Bias | mean (predicted - actual) | positive = over-paying forecast. Should be within a few dollars of zero |
| RMSLE | RMSE in log space | error in "orders of magnitude"; the scale the model actually trains on |
| Within10pct | share of claims predicted within 10% (or $1) | a business-friendly hit rate |
| **PI_coverage** | share of actuals inside the 90% interval | should be near 0.90 (0.948 here). Well below = intervals too narrow; well above = too wide |
| PI_median_width | median interval width in dollars | the price of the coverage |

### Denial (classification)

| metric | meaning | read it as |
|---|---|---|
| prevalence | actual denial rate | the base rate every other number is relative to |
| **PR_AUC** | area under precision-recall curve | the headline for a rare class. Baseline = prevalence (0.12). 0.51 = 4x baseline |
| **ROC_AUC** | rank quality | 0.5 random, 0.8 good, 0.9+ suspicious (check for leakage) |
| threshold | probability cut-off for the flag | chosen to maximise F1 on cross-validated probabilities; override with `DENIAL_THRESHOLD` |
| accuracy | share correct | nearly useless at 12% prevalence (always-approve scores 88%) |
| balanced_accuracy | mean of recall and specificity | accuracy that is honest about imbalance |
| precision | of flagged claims, share truly denied | the cost of false alarms for the review team |
| recall | of denied claims, share flagged | the cost of missed denials |
| specificity | of approved claims, share not flagged | |
| F1 / F2 | harmonic mean of precision and recall (F2 weights recall 2x) | pick F2 if a missed denial costs more than a false alarm |
| MCC | Matthews correlation | single honest number for imbalanced data, -1 to 1 |
| log_loss | penalises confident wrong probabilities | lower is better; compare across models only |
| **Brier** | mean squared error of the probability | 0.077 vs 0.105 for the prior; needs to be well below the baseline |
| **ECE** | expected calibration error | if the model says 30%, do 30% get denied? Under 0.05 is good. Matters because expected_paid multiplies by (1-p) |
| TP / FP / TN / FN | the confusion matrix at the threshold | |

### Weekly forecast

| metric | meaning | read it as |
|---|---|---|
| **MAE / RMSE** | as above, per week | |
| **MASE** | MAE / MAE of the naive one-step forecast in-sample | < 1 beats naive; the standard scale-free forecast metric; compare across series |
| **WAPE** | sum abs error / sum actual over the backtest | % of dollars or claims missed |
| sMAPE, MAPE | per-week % errors | MAPE undefined on zero weeks, so WAPE is preferred |
| Bias_pct | net over/under forecast as % of actuals | systematic drift; should be within a few % of zero |
| MAE_h1 .. MAE_h4 | MAE by weeks ahead | error should grow with horizon; if h4 < h1 the backtest is too small |
| PI90_coverage | share of backtest actuals inside the 90% interval, each origin scored with the other origins' residuals | 85% here for a 90% target: slightly narrow, expected with 12 origins |

## 7. The weekly learning loop (recommendation)

You asked: "as it predicts, can it also learn from that prediction every week?" Yes, with one
important correction. The model must learn from **what actually happened**, never from its own
predictions. Feeding predictions back as training data is a feedback loop that makes the
model confidently wrong. The loop below learns from adjudicated actuals.

```
             Monday                                          during the week
   +----------------------------+                    +---------------------------+
   | update last_week.csv       |                    | predict open_claims.csv   |
   |  1 score last week's       |   models,          |  -> P(denied), paid,      |
   |    claim predictions vs    |   forecast_next    |     interval, expected $  |
   |    actuals -> learning_log |------------------->|                           |
   |  2 score last week's       |                    | forecast_next.csv         |
   |    weekly forecast vs      |                    |  -> next 4 weeks $ and #  |
   |    actual -> learning_log  |                    +---------------------------+
   |  3 drift check (PSI)       |                                  |
   |  4 append, back up         |                                  |
   |  5 retrain + re-forecast   |<---------- adjudicated actuals --+
   +----------------------------+
```

`python claims_ml.py update last_week.csv` does all five steps. What to do with the output:

**Cadence.** Weekly is right for this data volume (about 100 claims per week). Retraining
costs 20 seconds. Daily adds nothing because the model needs adjudicated outcomes, and
adjudication takes days.

**Every forecast is kept.** `forecast_history.csv` accumulates every forecast ever made,
and `update` scores each one (all four horizon steps) as soon as its week is complete, exactly
once. Weeks with zero claims are treated as data gaps and not scored.

**`update` runs the full `train`, not `--fast`.** Fast mode can pick a different model
family (the stack instead of the single boosted model), and a weekly loop must not flip
families silently. Budget about two minutes per weekly run.

**Champion / challenger.** `update` retrains unconditionally. Before you put this in front of
finance, add the one rule that matters: only replace the model files if the retrained
model's holdout MAE (in `model_info.csv`) is not worse than the previous one's. The previous
`model_info.csv` is in the backup you already take. This is a five-line change and the
README calls it out rather than hiding it in code so you decide the tolerance.

**Read `learning_log.csv` monthly, not weekly.** One week's WAPE swings 8% to 20% on the
simulation because a single $60k claim lands or does not (see the notebook). Trend the
4-week rolling mean. Rising = investigate; drift report tells you which feature moved.

**Drift statuses.** PSI under 0.10 stable, 0.10 to 0.25 watch, above 0.25 drift. The
reference is the trailing 8 weeks, not all history, so January deductible resets do not
trip it. When a feature shows drift and `learning_log` error is rising in the same weeks,
that feature's relationship to paid has changed (new contract, new plan design), and a
retrain will fix it. Drift with no error rise is a population shift the model already
handles.

**What the simulation showed, honestly.** Over the last 8 weeks of the synthetic data a model
frozen for 26 weeks scored about the same as one retrained weekly (mean MAE $265 vs $260;
`simulate` uses the plain boosted model without tuning or smearing, so treat it as a relative
comparison), because the synthetic world drifts slowly. Retraining is not magic. Its value is (1) you have a scored,
dated record every week, (2) drift gets caught in weeks not quarters, (3) the model absorbs
step changes, which real claims data has and synthetic data does not.

**Interval feedback.** `learning_log.csv` records whether each weekly actual fell inside the
forecast interval. Over 20 weeks about 18 should. Fewer: raise `PI_LEVEL` or add history.

## 8. Tuning guide

All knobs are in the CONFIG block at the top of `claims_ml.py`.

| knob | default | raise it when | lower it when |
|---|---|---|---|
| `HOLDOUT_WEEKS` | 12 | you have 3+ years and want a sterner test | you have under 18 months |
| `CV_FOLDS`, `CV_REPEATS` | 5, 2 | metrics jump between runs (try 5, 3) | training time matters more than stability |
| `SEARCH_ITER` | 20 | after adding features, or overnight (60) | iterating on features (0 = skip) |
| `PI_LEVEL` | 0.90 | finance wants "almost never exceeded" (0.95) | intervals too wide to be useful (0.80) |
| `DENIAL_THRESHOLD` | auto (best F1) | false alarms cost more: set higher | missed denials cost more: set lower, or switch selection to F2 |
| `SIMPLE_TOLERANCE` | 0.02 | model size and explainability matter | every dollar of MAE matters |
| `HORIZON` | 4 | planning is monthly (5) or quarterly (13) | only next week matters |
| `BACKTEST_ORIGINS` | 12 | you have 3+ years (26 to 52 gives far better intervals) | history is under 18 months |
| `DRIFT_REF_WEEKS` | 8 | volume is low and PSI is noisy (13) | you want to catch change within a month (4) |
| `AS_OF` / `--as-of` | None (= end of the week containing the last service date) | always, in production: the date the extract is complete through | |
| `MAX_CATEGORY_LEVELS` | 200 | never above 255 | you want to force coarser groupings |
| `MONO` | 6 constraints | you have confirmed more directions with the business | a constraint is wrong for your plan design |

Model hyperparameters worth touching, in `hgb_reg()` and `clf_candidates()`:

- `max_depth` 3 to 6, `min_samples_leaf` 10 to 80, `l2_regularization` 0 to 10: the
  random search covers these. Larger leaves and shallower trees when the holdout MAE is
  much worse than the CV MAE (overfitting).
- `learning_rate` 0.02 to 0.1 with `max_iter` 300 to 1000: lower and longer is safer.
- `min_frequency=20` in the one-hot encoder: categories seen fewer than 20 times are pooled
  into "infrequent". Raise it if you have many rare provider types.

Forecasting: `LAGS`, `K_FOURIER` (seasonal harmonics; 3 is smooth, 6 follows sharp
holiday dips) and the members of `fc_ensemble()`.

## 10. Before you run this on real data

1. **Leakage.** Do not include anything known only after adjudication: allowed amount,
   adjustment codes, EOB fields, adjudication date. If ROC-AUC comes out above 0.95 or R²
   above 0.98, something leaked.
2. **Point-in-time features.** `prior_claims_12m`, `deductible_remaining` must be computed as
   of the service date, not as of today.
3. **Incurred but not reported (this one bites).** The most recent weeks are incomplete
   because claims arrive late, and the synthetic data has no submission lag so the demo cannot
   show it. In production: (a) set `AS_OF` to the date your extract is complete through, so
   partial weeks are excluded from the series; (b) score weekly forecasts only after the week
   has had 4 to 6 weeks to fill in, or aggregate by adjudication week instead of service week;
   (c) the weekly file you feed `update` should be "claims adjudicated this week" whatever
   their service date; dedupe by `claim_id` handles the late arrivals.
4. **Duplicates and reversals.** One row per final claim. Reversed or adjusted claims should
   be netted before they get here.
5. **Categorical labels.** Keep them stable week to week ("PPO" is not "ppo"). Unknown labels
   at predict time are handled (treated as missing) but reduce accuracy. A column with more
   than 200 levels (raw provider IDs, raw ICD codes) is rejected with a message: group rare
   levels into "Other" first. The boosted model has a hard limit of 255.
6. **Booleans and numbers.** `in_network`, `is_emergency`, `prior_auth` accept True/False,
   1/0, Yes/No, Y/N, T/F in any case; anything else stops the run with the offending values
   listed. Dollar columns must be plain numbers: strip `$` and `,` before loading. Both checks
   fail loudly on purpose; a silently empty feature is worse than a crash.
7. **PHI.** The model does not need names, addresses, dates of birth, or member IDs. Strip
   them before the CSV leaves the secure environment. `claims_backup_*.csv` files contain
   the full data; keep them where `claims.csv` is allowed to be.
8. **Holdout period.** If your denial rules changed 4 months ago, set `HOLDOUT_WEEKS` so the
   holdout is entirely after the change, and consider training only on post-change data.
9. **Run `train` twice with different `SEED` values.** If the selected model changes, the
   candidates are equivalent and you should pick on size and simplicity.

## 11. Limitations, stated plainly

- The synthetic data is easier than real claims. Paid is a near-deterministic function of
  billed amount, network status, plan and deductible plus 15% noise; R² of 0.96 reflects that.
  Expect 0.6 to 0.85 on real data with the same pipeline.
- The weekly dollar forecast has WAPE around 24% because a few catastrophic claims land at
  random. That is a property of the data, not the model. Large-claim pooling (section 5) is
  the fix.
- Two years of weekly history is the minimum. Seasonal naive is competitive with everything
  because there is only one prior year to learn from.
- 12 backtest origins give noisy interval estimates (85% observed for a 90% target). More
  history lets you raise `BACKTEST_ORIGINS`.
- The forecaster is univariate. It does not know about enrolment changes, plan-year
  boundaries or new provider contracts. If you know a change is coming, adjust the forecast
  by hand and say so.
- The notebook runs `train(fast=True)` for speed and may select a different model than the
  full run (the stack instead of the single boosted model). The shipped `.joblib` files and
  CSVs are always from the full run; run `python claims_ml.py train` last before shipping.
- No online learning. Retraining from scratch each week is deliberate: at 10k rows it is
  cheaper, simpler and more auditable than incremental updates.

## 12. Where this fits with your Snowflake platform

This package is the right tool when the dataset is small, the features are hand-curated,
and you want full control over every modelling choice, interval and metric. It runs
anywhere Python runs. When the customer's data volume grows or they want scoring inside the
warehouse, the same scikit-learn pipeline can be registered in the Snowflake Model Registry
and scored with Snowpark on a schedule, and the weekly `learning_log` table is a natural fit
for a Snowflake table feeding a dashboard. Cortex Analyst on top of that table lets the
finance team ask "how far off were we last month" in plain English. The two are
complementary: prototype and tune here, operate at scale there.
